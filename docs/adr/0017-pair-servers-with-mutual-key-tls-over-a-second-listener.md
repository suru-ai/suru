# Pair Servers with mutual-key TLS over a second listener

Supersedes the loopback-authentication clause of ADR-0001: a Server may now, off by default and only when its user enables Serving, accept connections from other machines' Servers. Serving opens a second listener on a fixed, user-configurable port speaking mutual TLS with self-signed certificates verified by raw pinned public key — no certificate authority, no hostnames — while the loopback listener, its dynamic port, and its descriptor-token authentication stay exactly as ADR-0001 left them, so enabling or disabling Serving starts or stops the second listener in-process through ordinary settings adoption and never restarts the Server or disturbs attached Clients. Trust is established by an Invite: a one-line `suru-v1-` string carrying the addresses the Serving user chose to offer, the Server's public key, and a single-use short-lived enrollment token that the next Invite supersedes; redeeming one forms a durable, one-way Pairing in which each side pins the other's key, reconnects on its own, and dies when either side deletes the other's entry — the redeeming side announcing its removal over the same pinned transport so the Serving side drops that Peer without a tombstone, while a Remote that does not answer within a short budget is forgotten locally all the same. A Peer gets everything except server administration — it cannot mutate the Serving side's Settings, stop it, or manage its Peers. A Client never dials a Remote itself: its own Server proxies the whole HTTP/SSE API under explicit `/v1/remotes/{name}` routing, dialing on demand only while some Client is looking at that Remote, and refusing a Pairing whose protocol version differs. Identity keys, enrolled Peers, and known Remotes live in the per-channel data directory with owner-only permissions, and per ADR-0008 none of that material ever reaches a Log.

Rejected: the Noise protocol (cleaner handshake, but it abandons the HTTP/SSE ecosystem the whole protocol rides on); delegating transport to SSH tunnels (least code, but it forfeits the paste-an-Invite pairing experience); rebinding the single existing listener behind a restart (ejects every attached Client and needs a new wire-level shutdown reason for what a second listener does for free); a long-lived shared secret in the Invite (a leaked scrollback line would be a forever-credential, where the enrollment token expires and steady-state auth is keys alone); and transparently merging Remote Sessions into the local catalog (bare SessionIds, Workspace paths, and Skill Catalogs from two filesystems would collide silently — a merged presentation may come later as a client-side Setting atop the same explicit routing).
