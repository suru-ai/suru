# Carry Attachments as bytes, uploaded at paste time and stored content-addressed in SQLite

An Attachment reaches the Server as bytes through its own upload route the moment it is pasted, is stored once in a content-addressed SQLite BLOB table joined to the Sessions that reference it, and is handed to every Provider as bytes: a data URL `image` item for Codex, a `blob` attachment for Copilot, a base64 image block for Claude. Prompts and Messages carry only an id, a label, and the label's span in the text, so snapshots, SSE updates, and the 64 KiB prompt command stay small and a client draws a preview by fetching the bytes by id.

Two of the three Providers also accept a file path, and a path would be the obvious shortcut for a local client. It was rejected because the Provider runs beside the Server that owns the Session, which for a Remote is another machine, and because a later viewer rebuilds the Transcript from the stored snapshot alone, so the bytes must outlive the client that pasted them. Inline base64 in the prompt command was rejected because it ties the command's size cap to image size and re-sends the bytes on every retry; uploading first makes retries idempotent by content hash, at the price of orphaned uploads, which a sweep deletes when they are older than an hour and referenced by no stored Prompt or Message. Files on disk beside the database were rejected because no Provider needs a path and one store keeps Session deletion transactional.

Suru never decodes pixels on the Server. It sniffs the format from magic bytes, admits only PNG, JPEG, GIF, and WebP, reads width and height from the header, and refuses anything over 5 MiB or more than ten per Prompt; Codex, Copilot, and Claude each resize on their own side already, and the 5 MiB cap is the tightest limit any of them publishes. A Model without vision is not detected: the Model Catalog carries no such capability, and Codex strips images silently for such Models, which is recorded as a follow-up rather than solved here. Deleting a Session reclaims only those of its Attachments that no other Session references and that were last uploaded longer ago than the same hour's grace, leaving younger ones for the sweep; since a client uploads an image, or uploads it again, right before binding it, that grace is what closes the race between a deletion and an admission still in flight, without counting references.
