# Represent Skill Invocations as Provider-neutral bindings

Suru represents an explicit Skill Invocation as the user's visible `$skill-name` text plus a typed binding to a server-issued opaque Skill identity. The server owns a Skill Catalog for each Provider and Workspace, validates every binding atomically at Prompt admission and again immediately before native delivery, and hands the Provider Session a neutral Prompt with ordered, deduplicated Skill identities. Each Provider adapter owns discovery and lowering: Codex receives its structured Skill inputs alongside the original text, Copilot expands one Skill through its native command API before sending the returned agent prompt, and Claude prefixes up to six native `/skill` invocations before the marker-free Prompt. Claude steer Prompts do not support Skill Invocations. The original composed Prompt and safe invocation records — opaque identity and canonical name, never a native path or command — remain the user Message and durable history.

## Considered Options

- **Treat `$skill-name` as text-only shorthand**: rejected because the Providers do not share that contract. Codex accepts a structured Skill input, Copilot requires command invocation, and Claude's explicit native syntax is `/skill-name`; silently sending text can produce an ordinary Prompt instead of an invocation.
- **Expand every Skill into instructions inside Suru**: rejected because it would bypass Provider-native loading, precedence, dynamic context, command behavior, and future Provider changes. It would also require Suru to read configuration that belongs behind the Provider boundary.
- **Expose native paths or command names to clients**: rejected because those identifiers leak server-local configuration, couple clients to Provider protocols, and let a client attempt to invoke capabilities outside its current Provider and Workspace.
- **Build one host-side Skill loader shared by Providers**: rejected because each Provider decides which Skills are enabled and user-invocable, how scopes override one another, and how invocation works. A shared loader would be a shallow abstraction over incompatible authority.
- **Let a changed catalog silently retarget a binding by name**: rejected because a same-named Skill may come from a different source or carry different instructions. A stale binding requires explicit user confirmation.

## Consequences

`ProviderRuntime` offers the effective Skill Catalog for a Workspace, while `ProviderSession` accepts neutral Skill-bearing Prompts and hides native lowering. Callers do not branch on Provider identity. A catalog contains only user-invocable Skills, safe display metadata, availability, the maximum number of distinct invocations, and supported Prompt deliveries. Opaque identities remain stable for the same Provider-native identity in the same Provider and Workspace across refreshes and server restarts; moving or replacing a Skill produces a new identity.

The first implementation keeps authoritative catalogs in memory, prefetched for the current context and invalidated by Provider-native change signals. A failed refresh makes the previous entries stale and non-invocable; partial results may retain valid entries with a warning. Persisted last-known presentation snapshots are deferred to GitHub issue #155 and will never become authoritative merely because they were cached.

The composer uses the selected Provider before a Session begins and the Session's fixed Provider afterwards. Typing `$` opens Skill autocomplete for the current token; confirming an entry replaces that range with its canonical `$skill-name` followed by a space without submitting. Bindings follow edits by range, exact unique typed or pasted names bind without opening autocomplete, ordinary unknown `$tokens` remain text, and stale or ambiguous bindings block atomic admission. Distinct Skills retain first-appearance order, repeats deduplicate, trailing prose punctuation is not part of a marker unless it belongs to the canonical name, and a Skill-only Prompt is valid.

Admission rejects the whole Prompt when any binding, delivery mode, or Provider limit is invalid. A catalog change between admission and delivery is checked again before any native input is sent; failure follows the existing visible Prompt or Turn failure path and never falls back to plain text. Historical Messages render from their stored safe invocation records rather than being reinterpreted through the current catalog.
