# Distinguish shutdown intent from connection loss

Managed clients treat an unexplained connection loss as a crash and recover by ensuring a server is running, but an authenticated final server event can identify an intentional manual stop or build replacement. A manual stop disables recovery and cleanly exits attached TUIs, while a replacement makes clients wait for and attach to the new instance; this prevents `suru server stop` from being immediately undone without sacrificing crash recovery.

A manual stop is also final for every server launched before it, not only for clients. Servers that lose an election wait out the winner's hold on the channel lock, so one still waiting when the winner is stopped would otherwise take the channel over and undo a stop that reported success. The stopping server therefore records its manual stop in the channel's state directory before it releases the lock, and answers the client that asked only once the record is durable — a stop that cannot be recorded is reported as failed, though the server still stops. Each launch follows the last stop recorded when it was asked for, and a server elected after a later stop exits without serving. A client holds to the stop it set out from through every probe, launch, stream, replacement wait and recovery attempt, so a later stop ends it — its launcher reports the stop, and a recovering client leaves as if it had received the stop's intent — before it can attach to, replace, or launch a server past the stop. Replacement and loss of standing record nothing, so a replacement still hands the channel on, and any launch made after the stop serves.
