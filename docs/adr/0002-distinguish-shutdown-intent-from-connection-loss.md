# Distinguish shutdown intent from connection loss

Managed clients treat an unexplained connection loss as a crash and recover by ensuring a server is running, but an authenticated final server event can identify an intentional manual stop or build replacement. A manual stop disables recovery and cleanly exits attached TUIs, while a replacement makes clients wait for and attach to the new instance; this prevents `suru server stop` from being immediately undone without sacrificing crash recovery.

A manual stop is also final for every server launched before it, not only for clients. Servers that lose an election wait out the winner's hold on the channel lock, so one still waiting when the winner is stopped would otherwise take the channel over and undo a stop that reported success. The stopping server therefore records its manual stop in the channel's state directory before it releases the lock, and answers the client that asked only once the record is durable — a stop that cannot be recorded is reported as failed, though the server still stops. Each launch follows the last stop recorded when it was asked for, and a server elected after a later stop exits without serving. A client holds to the stop it set out from through every probe, launch, stream, replacement wait and recovery attempt, so a later stop ends it — its launcher reports the stop, and a recovering client leaves as if it had received the stop's intent — before it can attach to, replace, or launch a server past the stop. Replacement and loss of standing record nothing, so a replacement still hands the channel on, and any launch made after the stop serves.

A stop is bounded however it goes, so no client, request or Provider can keep a stopping server alive. Clients hear its intent as it is accepted, and the server then lets go gracefully of all it can abandon — the requests in flight, the Serving listener, its Providers settling their Turns — within a deadline of that moment (10 seconds by default, over twice what its Providers' own stop timeouts can take). Whatever is left then is cut short: every connection is cut, dropping what was in flight on it, and every Provider process tree is killed. The steps that leave the channel sound for the next server — flushing storage, the Manual stop's record, removing its own runtime descriptor — are never skipped, but each is given up on once an overrun past the deadline runs out (5 seconds by default). Storage keeps what landed, whole. A stopping server writes to the channel's state directory only while it holds the election, or not at all: each write to it holds the election lock while it runs, so the lock is let go once the last is done, and a write still stuck when the process ends ends with it, unlanded, as the lock goes. No write of a stopped server can then undo a successor's descriptor or stop record. A record still unwritten when the overrun runs out degrades to a stop that could not be recorded: the client that asked for it is never told it succeeded, and should the process end before the write does, a server launched before the stop may serve. A descriptor that does not answer is left as a crash leaves it, for the next server to replace. All of that is kept by the server's own tasks, which a runtime whose workers are held — a Turn settling as the stop begins waits on storage that does not answer, holding the Session store — could never run, and the process then reports how its stop went to a stderr that may sit on that same directory. So a `suru __server` process is also held to a hard cutoff kept by a thread of its own, apart from the runtime: armed as its stop begins or a first shutdown signal arrives, it ends the process outright — `_exit` on Unix, `TerminateProcess` on Windows, running no exit handler — a margin (one second by default) past the stop's deadline and overrun, or that margin after the server has stopped, should the process still be running (status 124). The same thread hears the shutdown signals: a second one to a server already signalled — Ctrl-C pressed again — ends the process at once, with the status a shell reports for that signal (on Windows, the status a console's Ctrl-C leaves). Ending the process outright is safe, since its Provider process trees go with it, through their anchors on Unix and their Job Objects on Windows, SQLite's journal keeps storage whole, the lock goes as it ends, and its descriptor is left as a crash leaves it. A server run inside another process is never ended this way.
