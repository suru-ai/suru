# Read Activity tallies from storage without loading histories

Insights counts how the Agents worked: which Tools they used and how often those uses failed, how often their context was compacted, and how many Approvals they asked. Those are all Activities, and ADR-0022 keeps a Session's Activities in SQLite until that Session is opened; only its Turns are in memory from startup. Loading every history the range reaches to count its Activities would cost the first-open latency and memory ADR-0022 avoids, many times over. And hydrating a Session is not a pure read: it settles stale Turns and withdraws Prompts.

We decided the Insights read asks storage for Activity tallies directly and loads no history. Under the store lock it copies Turns and how each Session stands in its forest, as the metrics read does. Outside the lock it works out which Turns of which counted Sessions the interval holds. Then, on a blocking task, it queries the `activities` table for those Sessions, filtered by Session id in batches of a few hundred so no query binds more parameters than SQLite allows. Each row gives up its owning Turn and, through `json_extract` on its payload, only its kind, status, Tool name, MCP server, Compaction trigger, Context Fill before and after, Approval outcome, and Decision; one query reads Tools, Compactions, and Approvals together, so storage is read once per Insights read. A Command counts as "Command", a File Change as "File Change", a Tool Call under its name and MCP server, and each delegation — spawn or resume — as "Subagent", since each stretch of a Subagent's delegated work stands as a Subagent row of its own. A Compaction counts by trigger and status, and the freed share, (before − after) ÷ before, is averaged over those that completed knowing both figures with some context before; a failed or interrupted one left the context as it was. An Approval counts as asked, and then by its recorded Decision — Accept, Accept for Session, Decline, or Decline and Interrupt — as still waiting while it is answerable or its Decision is being delivered, or as expired where it settled with no Decision recorded: withdrawn, its Turn ended, no longer live, or its delivery uncertain, which Suru never records as a Decision made. No payload is deserialized and nothing is installed in the store. Storage keeps only those rows whose Turn the interval holds and streams each, decoded into the typed fields a tally reads, into a tally the Insights read owns: storage says what a row holds, and Insights what it counts toward. An Activity's time is its owning Turn's, taken from the in-memory Turn metadata.

The read goes to storage for every Session, including one already open in memory, so every Session is counted the same way. ADR-0022 has storage follow the in-memory history at idle moments and at every Turn boundary. So for a Session that is working now, storage may lag by Activities not yet saved: a Tool used moments ago may not be counted until the next save lands. Insights accepts that brief lag. It reports a range of past work, and a refresh after the save counts the use.

## Considered Options

- **Hydrate the Sessions the range reaches.** Rejected: it loads whole Transcripts to count a few fields, holds them in memory until eviction, and has hydration's side effects, so a read would change what it reads.
- **Count from memory where a Session is open, and from storage otherwise.** Rejected: two sources for one figure, each with its own rules about what has been seen. The lag it would avoid lasts only until the next save.
- **Keep running Tool counts on each Turn, or in a table of their own.** Rejected for now: it adds a second consistency contract that would need a migration and a backfill, as ADR-0022 declined for its summaries. Revisit only if the read proves slow, and then with an ADR of its own.
- **Filter by Turn id in SQL.** Rejected: `activities` is indexed by Session, not Turn. All time would bind every Turn id. Filtering by Session uses the index, and the Turn check in Rust is cheap.

## Consequences

- The Insights read loads no Session, moves no revision, and changes nothing. The no-hydration tests pin this.
- Reading the Tools costs time in proportion to the Activity rows of the Sessions with Turns in the range. Those rows' payloads are read from disk, and SQLite parses each for the fields asked of it, but none is deserialized.
- A Session working now may count a Tool it used recently only after its next save.
- A failed storage read fails the Insights read with a server error rather than reporting no Tools.
- Another Activity tally is a few more fields of the same query, never a second scan.
